Why LLM-D?

The Problem: Serving large models (70B+) requires distributed inference across multiple GPUs or nodes. Traditional Kubernetes primitives don't fit:

  • Deployment/StatefulSet — no leader/worker semantics, manual pod discovery
  • Naive scheduling — doesn't consider GPU topology (NVLink, PCIe, NUMA)
  • Single-phase serving — compute-bound prefill and memory-bound decode run on same GPU

The Solution: llm-d provides Kubernetes-native distributed inference with:

  • LeaderWorkerSet integration — automatic leader/worker coordination via LWS CRD
  • GPU-topology-aware scheduling — places leader/worker pods to minimize cross-node latency
  • Disaggregated serving (optional) — separate prefill/decode pods with KV cache reuse
  • KServe abstraction — users declare LLMInferenceService, llm-d handles the orchestration
Who Is LLM-D For?
  • Platform engineers building LLM serving infrastructure on Kubernetes
  • AI infrastructure teams running production inference at scale (1000+ req/s)
  • Enterprises moving from prototype to production LLM workloads
  • ML platform teams supporting multi-tenant LLM serving with LoRA adapters
  • SREs who need predictable latency, observability, and reliability for LLM endpoints
Architecture Overview

Component Stack (RHAI on Kubernetes):

  • User API: LLMInferenceService CRD (KServe v0.17.0)
  • Control Plane: KServe llmisvc-controller translates to LeaderWorkerSet
  • Orchestration: llm-d Inference Scheduler (v0.7.1), llm-d Workload Variant Autoscaler (v0.6.0), LeaderWorkerSet Controller (kubernetes-sigs/lws)
  • Service Mesh: Istio + Gateway API (HTTPRoute)
  • Runtime: vLLM (v0.18.0) with Ray distributed backend
  • Infrastructure: Kubernetes, cert-manager, GPU device plugins

Request Flow (Unified): Client → Gateway → vLLM Leader Pod → (Ray) → Worker Pods → Aggregated Response

Request Flow (Disaggregated): Client → Gateway → llm-d Router → Prefill Pod → KV Cache Storage → Decode Pod → Response

Key Concepts

LeaderWorkerSet (LWS): Kubernetes-native CRD (kubernetes-sigs, not llm-d) for leader+worker pod groups. Leader runs Ray head + vLLM coordinator. Workers run Ray workers + model shards. LWS controller auto-injects LWS_LEADER_ADDRESS env var for discovery.

Tensor Parallelism: Split model layers across multiple GPUs (within or across nodes). Each GPU computes its shard. Requires high-bandwidth interconnect (NVLink, RDMA). llm-d scheduler places pods to minimize cross-node latency.

Disaggregated Serving: Optional. Separate prefill (compute-intensive, A100) and decode (memory-intensive, L4/T4) pods. Prefill saves KV cache to shared storage. Decode loads KV cache for follow-up requests. llm-d router handles cache-aware routing.

KServe Abstraction: Users create LLMInferenceService CRD with parallelism params (tensor, pipeline, data, dataLocal). KServe llmisvc-controller calculates LWS size, selects hardware-specific config template (CUDA/ROCm/Gaudi), renders vLLM args, creates LWS + Service + HTTPRoute.

Getting Started

Prerequisites: Kubernetes cluster with KServe + llm-d installed (part of RHAI/OpenDataHub).

Example: Single-Node Inference (Llama-2-70b)

apiVersion: serving.kserve.io/v1alpha2 kind: LLMInferenceService metadata: name: llama-70b spec: model: uri: s3://models/llama-70b/ name: meta-llama/Llama-2-70b-chat-hf parallelism: tensor: 8 # 8-way tensor parallelism data: 1 # Single replica dataLocal: 8 # 8 GPUs on one node baseRefs: - name: v3-4-0-kserve-config-llm-template-nvidia-cuda worker: resources: limits: nvidia.com/gpu: "8" requests: memory: "400Gi" nodeSelector: node.kubernetes.io/instance-type: "p4d.24xlarge"

This creates: 1 pod with 8 GPUs. KServe translates to LeaderWorkerSet with size=1 (leader only, no workers).

Send Inference Request:

curl https://gateway/v1/models/llama-70b/chat/completions \ -H "Content-Type: application/json" \ -d '{"model":"llama-70b","messages":[{"role":"user","content":"Hello"}]}'
Production Benefits
  • Better GPU utilization — prefill and decode use different GPU profiles, disaggregation lets you right-size each
  • Lower P99 latency — KV cache-aware routing reduces cache evictions and recomputation
  • Higher throughput — decode pods can serve multiple requests in parallel without prefill compute overhead
  • Predictable scaling — add prefill or decode replicas independently based on bottleneck
  • Multi-tenant support — LoRA adapters share base model KV cache, scheduler routes by model affinity
  • Kubernetes-native — no external orchestrators, uses CRDs, integrates with Gateway API
